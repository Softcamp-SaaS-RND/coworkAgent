D17(자동 처리) · D7 · D8(피어 주소) · D9(로컬 웹UI 포트). 1a 점검 S8(원격 실행량 무제한) · S15(연결 슬롯 고갈)의 운영 쪽 짝이다.

### 지금 코드 사실 (main `35d5758`)

**큐잉**

- 받는 쪽은 **대화마다** 작업 하나가 DB 순서대로 하나씩 실행한다(`agent/chat.rs` `wake` · `process`). **대화 사이에는 상한이 없다** — 대화가 N 개면
  `claude -p` 가 N 개 동시에 뜬다(`spawn_blocking`). 대화 수 · 대기 건수 상한도 없다.
- 받는 쪽 글 상태 `queued` → `running` → `done`/`error` 는 **받는 PC 에만** 있다(`core/chat.rs` `State`). 보낸 쪽은 답(`Reply`)이 올 때까지 `보냄` 만 본다 —
  피어 프로토콜에 진행 상태 프레임이 없다(`net/proto.rs`).
- 보낸 쪽 CLI `ask` 는 답을 **30분**(`cli.rs` `WAIT_LIMIT`) 기다린다. 받는 쪽 대기가 길어지면 실행 전에 CLI 가 먼저 포기한다.
- 거절 선례: 집중(D17 개정)은 새 오류 코드 `focus` 로 즉시 거절 → 보낸 쪽 "상대가 집중 중" · 다시 보내기.

**포트** (실측 — 13.5 시간 실행 중 앱)

| 포트 | 정하는 법 | 실측 | 정리 |
|---|---|---|---|
| 웹UI | `127.0.0.1` 임의 포트, 실행마다 바뀜 · `instance.json` 에 기록 | Listen 1 · Established 2(브라우저) | 종료 시 `instance.json` 삭제(`main.rs` `on_quit`). 비정상 종료면 파일이 남지만 다음 실행이 덮어쓴다 |
| 피어 | `0.0.0.0:47100` 고정, **사용 중이면 조용히 임의 포트**(`net/node.rs` `bind_peer_port`) | Listen 1 | — |
| 나가는 연결 | 요청마다 새 TLS 연결 → 닫음 | 47100 관련 `TIME_WAIT` · `CLOSE_WAIT` 0 | — |

- **누수는 관찰되지 않았다**(13.5 시간 · 소켓 4개). 프로세스가 끝나면 OS 가 포트를 거둔다.
- 실제 빈틈 1 — **47100 이 사용 중이면 임의 포트로 열고 상대에게 알리지 않는다.** 상대는 페어링 때 받은 주소(`peers.addr`, Hello 때만 갱신 —
  `core/peers.rs`)로만 보내므로 이 PC 에 닿지 못한다. 다시 페어링하면 승인이 초기화된다. IP 가 바뀐 경우(DHCP)도 같다.
- 실제 빈틈 2 — 누가 47100 을 잡고 있는지(예: 끝나지 않은 이전 coworkAgent) 사용자에게 보이지 않는다. 로그 경고 한 줄뿐.
- 확인 필요 — 실행 중인 `claude -p` 자식이 소켓 핸들을 물려받아 앱이 죽은 뒤에도 포트를 잡는지(Rust · tokio 소켓은 상속 안 됨으로 만들어지는 것으로
  안다 — 실측 전). 자식은 Job Object 로 앱과 함께 끝난다(`runner.rs`).

## 범위

- **받는 쪽 실행 대기열**: PC 전체 동시 실행 상한(설정, 기본 2) — 넘는 요청은 대기열에 넣어 도착 순서로 처리(거절 없음, 결정 1). 대화 안 직렬(D19)은 그대로.
- **보낸 쪽 안내**: 받는 쪽이 접수 때 "대기 중 — 앞에 k건" 을, 실행 시작 때 "처리 중" 을 보낸다(새 프레임). 보낸 쪽 글 아래 "상대 PC 에 처리 중인 작업이
  많아 응답을 기다립니다(앞에 k건)" · CLI `ask` 는 같은 상태를 출력하고, 대기 중인 동안은 30분 기다림에서
  빼지 않는다(결정 4).
- **받는 쪽 화면**: 내 PC 의 실행 중 · 대기 건수와 목록(실행 상세 패널).
- **포트 관리**: 47100 을 못 열면 잡고 있는 프로세스(이름 · PID)를 트레이 · 웹UI 에 알림 · 임의 포트로 열었으면 페어링된 상대에게 **새 주소 통지**
  (키 고정 TLS 로 인증된 상대만 · 승인 유지) · 설정 화면에 웹UI 포트 · 피어 포트 · 열린 연결 수 표시 · 종료(정상 · 강제 · `claude` 실행 중)
  뒤 두 포트가 풀리는지 검사.

## 제외

- 우선순위 · 상대별 공정 분배(라운드 로빈) — 도착 순서(FIFO)만. 필요해지면 후속.
- 대기열을 앱 재시작 너머로 보존 — 지금처럼 재시작 시 `running` 은 실패 답, `queued` 는 다시 실행(현행 유지).
- 피어 포트를 사용자가 바꾸는 설정 — 결정 5.
- 바쁨 거절 · 대기 한도 — 결정 1.
- 연결 슬롯 고갈 DoS(1a S15) — 원장 `#01 R2-F2`.

## 성공 기준

- A1: 동시 실행이 상한을 넘지 않는다 — 상한 2 에서 서로 다른 대화 5건이 동시에 오면 실행 2 · 대기 3, 끝나는 대로 도착 순서로 실행된다.
- A2: 요청이 몰려도 거절되지 않는다 — 상한 2 에서 서로 다른 대화 30건이 오면 30건 모두 대기열에 들어가 도착 순서로 실행되고 모두 답한다.
- A3: 대기에 들어간 요청을 보낸 쪽 글 아래 "처리 중인 작업이 많아 응답을 기다립니다(앞에 k건)" 이 보이고, 실행이 시작되면 "처리 중" 으로 바뀐다.
- A4: CLI `ask` 가 대기 · 처리 중 상태를 출력하고(`--json` 포함), 대기 시간 때문에 실행 전에 포기하지 않는다.
- A5: 받는 쪽 화면에 내 PC 의 실행 중 · 대기 건수와 목록이 보인다. 동시 실행 상한은 설정에서 1 ~ 8 로 바꾸고 이 PC 에 저장된다.
- A6: 47100 을 다른 프로세스가 잡고 있으면 시작 시 그 프로세스 이름 · PID 가 트레이 · 웹UI 에 보인다.
- A7: 임의 포트로 연 경우 페어링된 상대가 승인 초기화 없이 새 주소로 이 PC 에 닿는다(새 주소 통지는 키가 맞는 상대만 반영).
- A8: 정상 종료 · 강제 종료 · `claude` 실행 중 강제 종료 뒤 5초 안에 웹UI · 피어 포트가 모두 풀리고(다시 실행하면 47100 을 연다), 남은 `instance.json` 이 다음
  실행을 막지 않는다.
- A9: 설정 화면에 웹UI 포트 · 피어 포트(고정 / 임의) · 열린 연결 수가 보인다.
- A10: 기존 테스트 · 웹UI 테스트 green, 경고 0.
