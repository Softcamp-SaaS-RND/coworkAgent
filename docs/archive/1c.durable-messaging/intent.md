### 지금 코드 사실 (main `5c63e66`)

- **받는 쪽은 이미 DB 큐다** — 받은 실행 요청은 `queued` 로 저장된 뒤 대화 작업이 꺼내 `claude -p` 로 실행한다(`agent/chat.rs` `wake` · `process`, D19).
  재시작 때 `queued` 는 다시 실행, `running` 은 실패 답(`recover`).
- **보내는 쪽에는 저장 단계가 없다** — `Message` · `Post` · `Reply` · `Relay` · `Done` · `Progress` 를 바로 `node.send` 한다(`chat.rs` 7곳). 실패하면:
  요청은 `sent` 유지 + "전달 확인 안 됨 … 다시 보내세요"(사람이 다시 보냄), 답은 `undelivered` 로 남고 **다시 보내지 않는다**, 진행은 로그만(1b 원장
  `#1b R1-P`). D7 의 "보관했다가 재전송" 이 구현되지 않았다.
- **CLI `ask` 상태는 CLI 프로세스 메모리에만** — 1초마다 대화 글을 읽는다(`app/cli.rs` `wait_reply`). CLI 가 죽으면 추적이 끊기고, `queued` 를 본 뒤
  상대가 사라지면 30분 시계가 멈춘 채 끝나지 않는다(1b 원장 `#1b R2-CLI`). 같은 질문을 다시 실행하면 새 실행이 된다.
- **30초 접속 확인** — 페어링된 상대마다 30초에 TLS 연결 1회(`net/node.rs` `watch_presence` → `Ping`/`Pong`). 쓰임: 온라인 표시(75초 · `ONLINE_WITHIN`) ·
  집중 표시 · 1b 주소 따라가기(`Ping.port`). `seen_at` 은 `Pong` 받을 때만 갱신(그 밖 1곳 — `chat.rs` 받은 요청).
- **처리경과** — 보낸 쪽이 아는 것은 1b 의 `queued(앞 사람 수)` · `running` 뿐. `claude -p` 는 `--output-format json`(끝에 한 번). 2.1.296 은
  `--output-format stream-json`(실시간 이벤트, `--verbose` 필요) 을 지원한다(`claude --help` 확인).
- RabbitMQ 는 별도 브로커(Erlang) 프로세스가 필요해 단일 실행 파일(D2 · D3)과 맞지 않는다 — 같은 의미(저장 · ack · 재시도 · 실패 보관)를 지금 쓰는
  SQLite 로 만든다(사용자 수용).

## 범위

- **보내는 쪽 outbox(SQLite)**: 상대에게 가는 대화 프레임(`Message` · `Post` · `Reply` · `Relay` · `Done` · `Progress`)은 먼저 DB 에 적고 상대별 줄이
  보낸다 — 응답(ack)을 받으면 끝, 전송 오류면 간격을 늘려 다시, 한도를 넘으면 실패 보관 + 화면 표시. 앱 재시작 뒤에도 이어 보낸다. 받는 쪽은 지금처럼
  uuid 로 한 번만 받는다(중복 무시).
- **상태 질의 프레임**: 보낸 쪽이 필요할 때 상대에게 그 글의 상태(대기 · 앞 사람 수 / 실행 중 / 끝남 / 모름)를 묻는다. 끝났는데 답이 안 왔으면 받는 쪽이
  답을 다시 보낸다.
- **CLI 트랜잭션**: `ask` 는 앱 DB 에 트랜잭션을 만들고 그 상태를 본다 — 중복 키(`--id`)로 다시 실행해도 새 실행 없음 · CLI 가 죽어도 `wait <tx>` 로 이어
  받기 · 상대가 오래 닿지 않으면 정해진 종료 코드로 끝(무기한 대기 없음).
- **접속 상태 = 통신할 때만**: 30초 주기 확인을 없애고, 주고받기에 성공할 때마다 `seen_at` 갱신. 화면은 "마지막 통신 n분 전". 시작 때 1회 주소 알림 ·
  웹UI 를 열 때 확인.
- **처리경과 콜백**: 받는 쪽이 `claude -p` 를 실시간 이벤트로 돌려 실행 중 단계 요약을 진행 이벤트로 보낸다(outbox) — 보낸 쪽 웹UI 글 아래 · CLI(평문 ·
  `--json`) 에 보인다.
- **README 개편**: 사용자 관점(목적 · 이점 · 주요 기능 요약 + 매뉴얼 링크), 기술 내용은 매뉴얼로.

## 성공 기준

- A1: 상대가 꺼져 있을 때 보낸 실행 요청은 이 PC 에 남고, 상대가 다시 켜지면(이 PC 를 다시 켠 경우 포함) 사람이 다시 보내지 않아도 전달 · 실행 · 답이 온다.
- A2: 답 · 완료 표시 · 진행도 같은 보장 — 답을 보낼 때 묻는 쪽이 꺼져 있었어도 다시 켜지면 답이 도착한다(지금의 "답 미전달" 이 남지 않는다).
- A3: 같은 글은 몇 번 다시 보내도(재시도 · 앱 재시작 · CLI 재실행) 상대에서 한 번만 실행된다.
- A4: 한 상대가 닿지 않아도 다른 상대로 가는 글 · 진행이 늦어지지 않는다.
- A5: 재시도 한도를 넘은 글은 실패 보관으로 옮겨 화면에 "보내지 못함" 과 다시 보내기가 보인다.
- A6: CLI `ask --id <키>` 를 다시 실행하면 새 실행 없이 같은 트랜잭션의 결과를 받는다. CLI 가 중간에 죽어도 `wait <tx>` 로 이어 받는다.
- A7: CLI 는 상대가 대기 · 실행 중임이 확인되는 동안 계속 기다리고, 상대에 정해진 시간 동안 닿지 않으면 정해진 종료 코드로 끝난다 — 무기한 대기가 없다.
- A8: 주기적 접속 확인이 없다 — 유휴 상태에서 피어 연결이 생기지 않는다. 주고받기에 성공하면 접속 시각이 갱신되고 화면은 "마지막 통신 n분 전" 을 보인다.
- A9: 1b 의 바뀐 포트 · IP 따라가기는 그대로 된다(주기 확인 없이).
- A10: 실행 중 단계 요약이 보낸 쪽 웹UI · CLI(평문 · `--json`)에 실행이 끝나기 전에 보인다. 상대에게 가는 요약에 도구 입력 · 파일 경로 · 모델 글은 없다.
- A11: 기존 테스트 · 웹UI 테스트 green, 경고 0.
- A12: README 는 목적(웹서버 없음 · AI API 비용 없음 · 페어링 코워크 · 대화 서버 저장 부담 없음) · 주요 기능 요약 · 매뉴얼 링크 중심이고, 기술 내용(통신 구조 · 프로토콜 · 보안 경계 · 빌드)은 매뉴얼에 있다 — README 의 링크가 모두 살아 있다.
