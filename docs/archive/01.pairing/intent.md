# intent — 01.pairing

승인: 2026-10-11

## 왜
PC 간에 말을 주고받으려면 먼저 "상대가 누구인지" 를 정하고 그 상대만 받아들이는 통로가 있어야 한다. 지금 실행 골격
(00.skeleton)에는 신원도 피어 연결도 없다 — Phase 0 의 둘째 조각으로 설치별 신원 · 내 정보 보기 · 수동 주소 연결 ·
지문 비교 페어링 · 공개키 고정 TLS 를 세운다. 02.agent-roundtrip 의 메시지는 이 통로 위로만 오간다 — 출처:
[masterPlan](../../masterPlan.md) D7(수동 주소) · D8 · S4 · SC2 · Phase 로드맵 0 · 자동 진행 위임(2026-10-11 "완료를 목표로
개발 진행해.").

## 범위
- 설치별 ed25519 신원 키(D15 경로 `identity.key`) · 지문
- 트레이 메뉴 "내 정보 보기"(S4) → 웹UI 내 정보(이름 · PC 이름 · 지문 · 수신 주소)
- 피어 수신 포트(LAN) · TLS 1.3 + raw public key(RFC 7250) 상호 인증 · 공개키 고정
- 수동 주소(IP:포트) 추가 · 양측 지문 비교 승인 페어링 · 피어 삭제 · 피어 목록(웹UI)
- 미페어링 피어의 페어링 외 요청 거부(SC2 앞부분) · 페어링 확인용 `ping`
- SQLite 스키마 2(피어 표)

## 성공 기준
- A1: 첫 실행에 신원 키가 D15 경로에 생기고 재실행해도 지문이 같다. 키 파일이 손상되면 새로 만들지 않고 시작을 멈춘다.
- A2: 트레이 메뉴 "내 정보 보기" 가 웹UI 의 내 정보(이름 · PC 이름 · 지문 · 수신 주소)를 연다.
- A3: 피어 통신은 TLS 1.3 상호 raw public key 인증이다 — 고정한 키와 다른 상대 · 클라이언트 키를 내지 않는 상대는 연결되지 않는다.
- A4: 수동 주소 추가 뒤 **양쪽 사람이 모두 승인해야** 페어링이 끝난다 — 한쪽만 승인한 상태는 페어링이 아니다.
- A5: 페어링하지 않은(또는 삭제한) 피어의 페어링 외 요청은 거부되고, 페어링한 피어의 요청은 통과한다.
- A6: 원격 입력에 상한이 있다 — 큰 프레임 거부 · 이름 정제 · 내가 승인하지 않은 피어 수 상한.
- A7: Windows PC 2대가 실제 LAN 에서 서로 주소를 추가 · 지문 비교 · 양측 승인으로 페어링된다.
- A8: 루트 `PROJECT.md` 검증 명령의 테스트 · 경고 0 · 의존 경계 행이 통과한다.

## 결정
자동 진행 위임(masterPlan) — 권장안으로 정했다.

- P1 신원 = ed25519 PKCS#8 파일 `identity.key`(D15 루트). 쓰기는 임시 파일 → 이름 바꾸기. 손상 시 시작 실패(재생성하면 기존
  페어링이 조용히 깨진다).
- P2 지문 = SHA-256(SPKI DER) 앞 16바이트, 대문자 hex 4자리 8묶음(공백 구분). 기각: 앞 8바이트 — 사람 비교용으로 짧지만
  위조 여유가 작다.
- P3 피어 수신 = `0.0.0.0:47100`, 사용 중이면 OS 임의 포트로 대신 열고 내 정보에 실제 포트를 보인다.
- P4 페어링 = A 가 B 주소 추가 → `hello` 교환으로 양쪽에 대기 기록 → 각자 지문 비교 뒤 "승인" → 상대에 `approve` 통지 →
  양쪽 모두 승인이면 페어링. 삭제 = 내 기록 삭제 + 상대에 `remove` 통지(실패해도 내 쪽은 삭제).
- P5 미페어링 상대에게 허용하는 요청은 `hello` · `approve` · `remove` 뿐, 나머지는 `not_paired`.
- P6 원격 입력 상한: 프레임 64 KiB · 이름 64자(제어 문자 제거) · 연결당 10초 · 동시 연결 32 · 내가 승인하지 않은 피어 32.
- P7 내 정보의 이름 = OS 사용자 이름, PC 이름 = 호스트 이름(편집 없음). 트레이 "내 정보 보기" = 웹UI `/#me`.
- P8 (적대적 평가 라운드 1 반영 · 자동 진행 위임) 처음 보는 키의 hello 는 웹UI "페어링 받기" 가 연 창(5분) 안에서 1건만 받는다
  — 창 밖은 `closed`. 아는 키의 hello(다시 추가)는 창과 무관하며 **양쪽 승인을 지우고** 처음부터 페어링한다. 기각: 미승인
  기록 TTL · 출처별 속도 제한만 두기 — 창 없이 받으면 LAN 의 미페어링 호스트가 슬롯을 계속 채울 수 있다.
  라운드 2 반영으로 창은 **초대 코드**(8자, `ABCD-EFGH`)에 묶인다 — 코드가 맞는 hello 만 창을 소비하고 틀린 코드는 창을
  닫지 않는다(선점 불가). 받는 쪽이 주소 · 코드 · 지문을 상대에게 알려 준다.
- P9 (라운드 2 반영) hello 마다 보낸 쪽이 페어링 세대(`round`, 16바이트 난수)를 만들어 양쪽이 저장하고, approve 는 같은 세대에만
  적용된다(이전 세대는 `stale`). 수신 연결은 출처 IP 당 동시 4개 · 연결당 3초(인증 전 느린 연결 포화 방지), 전체 32 를 넘으면
  accept 를 멈추지 않고 바로 끊는다.

- P10 (사용자 지시 2026-10-11 "초대코드를 다른 메신져를 통해서 전달 , 적용이 편리하도록 ux 제공") "페어링 받기" 는
  메신저로 보낼 **초대 텍스트**(사람용 2줄 + 토큰 `agentnetwork-invite:v1/{주소}/{코드}/{지문 hex}`)와 "초대 복사" 를 준다. 받은
  쪽은 "초대 붙여넣기" 에 메시지를 통째로 넣으면 토큰을 찾아 **초대의 지문으로 서버 키를 고정**해 연결하고(다르면 hello 전에
  끊김) 추가 · 내 승인까지 한 번에 한다 — 붙여 넣는 행위가 그 사람의 승인이다(A4 유지: 상대 쪽은 여전히 승인 필요).
  주소 · 코드 직접 입력은 접힌 보조 경로로 남긴다.
