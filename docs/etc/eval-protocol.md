# 적대적 평가 프로토콜

> **plan 의 평가 항목을 쓸 때와 구현 완료 후 평가할 때만 여는 문서.**
> 목적·계약은 [ddd-workflow.md](ddd-workflow.md) "적대적 평가자". 여기는 그 실행 세부다.

## 규약

1. **평가 항목은 plan 단계에서 고정한다** — 구현 전이라 "만든 것에 맞춘 채점" 이 불가능하다.
   여력이 있으면 **채점 기준 작성 주체도 계획 주체와 분리**한다(권장) — 시점 분리는 *채점하기
   쉬운 기준 고르기*는 못 막는다.
2. **항목은 gate 형식으로 적는다.** 아래가 **정본**이며 `tools/check_gates.py` 가 정확히 이
   형식을 파싱한다.

   ```text
   - [ ] E1: {A{n} — 검증 가능한 결과, 낯선 사람이 판정할 수 있게}
     CHECK: {실행할 셸 명령}
     EXPECT: {출력에 있어야 할 부분 문자열, 또는 /정규식/}
     EVIDENCE: pending
   ```

   - **제목 첫머리에 덮는 intent 성공 기준 `A{n}`**(둘 이상이면 `A1·A3 …`) — `check_ddd_docs.py` 가
     대조한다(intent-protocol 규약 4). 어느 기준도 아닌 gate 는 번호 없이 적는다.
   - **EXPECT 가 정확값, CHECK 가 판정 방법.** "적절히" 대신 수치·literal 로,
     **성공일 때만 나오는 줄**(`8 passed`)을 고른다. 양쪽에 다 나오는 줄(`done`)은 안 된다.
   - 성공 = **rc 0 이면서** EXPECT 가 `stdout+stderr` 에 있는 것. `1 failed, 23 passed` 는
     rc=1 인데 `/passed/` 를 포함한다. **EXPECT 생략 시 rc 만** 본다. `CHECK` 가 없으면
     **수동 gate**(EVIDENCE 를 사람이 적는다).
   - `/.../` 는 정규식(플래그 없음), 그 외는 부분 문자열. **EXPECT 는 ASCII.**
     `shell=True` 가 지나는 콘솔 코드페이지에서 비-ASCII 는 깨진다.
   - 🔴 **`CHECK` 는 셸로 실행된다.** `plan.md` 는 **실행되는 파일**이고, 노출 등급은 그
     트리에서 `pytest`·`make` 를 돌리는 것과 같다. **신뢰하지 않는 브랜치·PR 트리에서는
     돌리지 않는다.** 남의 diff 는 `--list` 로 명령을 먼저 읽는다.
   - 🔴 **`CHECK` 는 `shell=True` 의 기본 셸에서 돈다 — Windows 는 cmd.exe.** `./bin/x`·bash
     전용 구문은 실행조차 안 되고 FAIL 로 위장된다. cmd·bash 양쪽에서 도는 형태로 쓰고, plan
     에 적기 전에 `subprocess.run(cmd, shell=True)` 로 한 번 재현한다.
   - **자기 Task 폴더는 `{TASK}` 로 가리킨다.** 치환되는 placeholder 는 이것뿐이다. 경로를
     글자로 박으면 종결(`git mv` → archive) 하는 순간 깨진다.
   - 🔴 **자기 원장을 읽는 CHECK 를 두지 않는다.** 원장은 *이전 실행*의 결과라, 자기 실패를
     읽고 다시 실패하는 **고정점**이 된다.
   - **정확값을 모를 때는 범위로**(`/37[2-9][0-9] passed/`). `/passed/` 는 *대량 삭제도 통과*.
   - 🔴 **부정형 단정은 모집단 크기를 함께 단정한다.** "없어야 한다"(diff 0·grep 0·위반 0)는
     **검사 대상이 없을 때도 통과**한다. 경로가 사라지면 아무것도 검사하지 않으면서 영원히
     초록이다. FAIL 은 눈에 띄지만 헛통과는 안 띈다. **대상이 N개임**과 **위반 0** 을 한 줄로
     함께 출력하고 EXPECT 로 **둘 다** 단정한다.

     ```text
     - [ ] E7: 계약 모듈 4종이 실재하고 임시 주입 마커가 0건이다
       CHECK: python -c "import glob;fs=glob.glob('src/codec/*.py');v=sum('TEMP_INJECT' in open(f,encoding='utf-8').read() for f in fs);print(f'targets={len(fs)} violations={v}')"
       EXPECT: targets=4 violations=0
     ```

     - `targets=4` 가 있어야 사라짐이 `targets=3` 으로 드러난다. **대상 개수가 계약이다.**
     - `python -c` 한 줄은 cmd·bash 양쪽에서 같게 돈다(바깥 큰따옴표 · 안쪽 작은따옴표만).
       `$(…)`·`wc`·`grep -rl` 은 cmd.exe 에서 실행조차 안 된다.
     - 🔴 `print` 로 끝나 **rc 가 항상 0** 이므로 위 "rc 0 이면서" 의 **명시적 예외**다.
       판정 전부를 EXPECT 가 진다. EXPECT 를 빼면 무조건 통과가 되어 무의미가 즉시 드러나고,
       원장에 `WEAK` 로도 표시된다.
     - **부분 문자열로 단정한다.** stderr 한 줄만 섞여도 `/^…$/` 앵커는 깨진다.
     - **"무변경" 은 기준 커밋 sha 를 글자로 박는다**(Task 착수 직전 = plan 승인 커밋).
       `HEAD~1` 은 *같은 Task 안 세 커밋 전 변경*을 통과시키는 완화된 단정이다. 기준선이
       필요 없는 형태(위 `violations` 수)로 쓸 수 있으면 그쪽이 낫다.
   - **보고에 등장할 수치는 각각 자기 gate 를 가진다.** 기억으로 적은 수치가 오보의 주경로다.
   - 항목 수 **5~12개**. 2개면 Task 가 덜 명세됐고, 20개면 Task 를 쪼갠다.
   - **plan 승인 대상은 항목·EXPECT.** `CHECK` 는 구현 중 보정 허용. EXPECT 변경은
     **항목 변경**이며 규약 3 을 탄다.
3. **구현 중 항목 변경은 plan 개정 → 사용자 승인으로만**([ddd-workflow.md](ddd-workflow.md) "적대적 평가자" 3).
   - 승인 **전**에 적은 개정 줄에는 **`사용자 미승인`** 표기. 종결(`report.md`) 시 남아 있으면
     문서 규약 체커가 FAIL 한다.
   - 승인된 개정은 `plan.md` 에 **개정 기록**(항목·무엇을·승인일·사유)으로 남긴다.
4. **평가는 구현 완료 시점에 수행하고 `eval.md` 로 남긴다.** 항목별 **충족 / 미충족** +
   **근거(명령·출력)** + 미충족 시 조치. 기계 판정은 `check_gates.py` 가 `eval.md`
   **`## 평가 원장`** 에 쓴다(`{python 호출형} tools/check_gates.py docs/tasks/{NN.기능명}`).
   - **`plan.md` 는 읽기 전용**(승인된 계약). 도구는 원장만 쓴다.
   - 원장에 **측정 커밋 sha** 가 기록된다. 코드를 바꾸면 재실행해 갱신한다 — 신선도 판정은
     순환 방지 4.
   - **미충족(UNMET)** 셋 중 하나: ①박스가 비었고 `ABANDON:` 도 없다 ②박스는 체크됐는데
     `EVIDENCE:` 가 `pending`(**증거 없는 체크는 미체크보다 나쁘다**) ③CHECK 출력이 EXPECT 불일치.
   - **정말 불가능한 항목은 지우지 않는다.** `ABANDON: E{n} {사유}`(사람이 적는 독립 줄)를
     원장에 적고 보고한다. 드러난 포기는 정직하고, 조용한 범위 축소는 아니다. **사유 없는
     `ABANDON:` 은 포기가 아니라 미충족**이다.
   - **약한 gate 는 `WEAK: E{n} {사유}`**(기계가 매 실행 다는 독립 줄)로 표시된다.
     `EXPECT` 없음(rc 만 봄) · `CHECK` 없음(수동). 판정에는 영향이 없고 **셀 수 있게** 하는
     것이 목적이다. 늘면 그 Task 가 기계 판정 가능한 형태로 명세되지 않은 것이다.
   - **근거는 판정을 가른 줄만**(도구가 자른다). 로그 전문을 붙이지 않는다.
   - 종결 시 원장은 plan 과 **항목 단위 대조**된다(id·제목·CHECK·EXPECT·순서). **조용한
     축소**를 막는다. `ABANDON` 도 **계약에 있는 id** 만 인정된다.
5. **평가자는 구현 세션과 분리된다** — 수단은 [ddd-workflow.md](ddd-workflow.md) "도구 전제". **분리가 계약**이다.
6. **적대적으로 본다.** 기본 질문은 "무엇이 빠졌나".
   - **intent 의 성공 기준(A*)에 gate 가 없거나 덮지 않는 항목** — plan 이 의도를 조용히 줄인
     자리다([intent-protocol.md](intent-protocol.md) 규약 4). 첫 질문은 plan 이 아니라 intent 에서 시작한다.
   - 명세에 있는데 **구현되지 않은** 기능·분기·옵션
   - **범위가 좁아진** 구현(한 대상만·한 경로만·happy path 만)
   - **완화된 단정**(테스트가 원래 기준보다 약하게 검사) · **경계값 미검사**
   - **조용한 실패**(`ok=True` 인데 결과가 비어 있는 유형)
   - **실경로를 우회한 검증.** 제품에 박은 테스트 훅·환경변수 스위치, 내부 함수 직접 호출,
     헤드리스 왕복으로 "동작 확인" 을 대신한 곳. 사용자가 실제로 지나는 진입점(설치·배포된
     산출물·실제 이벤트·실제 권한)을 지났는지 본다. 그런 훅은 릴리스 산출물에 잔존 금지.
   - **검사 대상이 사라진 gate**(규약 2 부정형 단정). 초록인 gate 가 *무엇을* 검사했는지
     되묻는다. 원장의 `WEAK` 가 그 후보 목록이다.

## 평가 실행 절차 (고정)

구현 완료 후 `report.md` **전에** 실행한다. 아래는 예시다. 다른 수단이면 명령만 바꾸고
**기준선·focus·라운드 상한**은 그대로 지킨다.

```text
BASE = <Task 착수 직전 커밋 sha>          # plan 승인 시점
/codex:adversarial-review --base $BASE --scope branch
  "intent.md 성공 기준 A* ↔ plan.md 평가 항목 E1~En ↔ 구현 대조. 특히: 미구현 기능·분기, 범위가 좁아진 구현,
   완화된 테스트 단정, 경계값 미검사, ok=True 인데 결과가 비는 조용한 실패."
```

- **반드시 `--base` 를 준다.** 없으면 빈 diff 가 나오고, 그 `findings 0` 은 **"리뷰할 patch
  없음"** 이지 승인이 아니다.
- 리뷰 결과는 **라운드마다 그 커밋에** `eval.md` 로 남긴다 — **원문 그대로** + plan 항목 대조표.
  커밋 메시지는 기록이 아니다.
- **지적은 코드 사실로 검증한 뒤 반영한다.** 실재부터 확인하고, 사실이면 수정, 아니면 반박을
  근거와 함께 적는다.
- 수정 후 **같은 base 로 재리뷰**. **최대 3 라운드**(리뷰 1 + 반영 1 = 1 라운드). 상한에서
  멈추고 남은 지적은 `eval.md` **`## 미조치 지적`** 절에 **표**(`| 지적 | 판단 | 사유 |` — 원문
  요지 · 사실/오탐 · 미조치 사유)로 기록한 뒤 계속 여부를 사용자에게 묻는다. 남은 지적이 없으면
  그 절은 `없음` 한 줄(산문·bullet 금지 — 체커가 표 행과 [overview/ledger.md](../overview/ledger.md) 원장을 대조한다).
  🔴 **종결하는 `eval.md` 에는 이 절이 반드시 있다** — 도구는 원장만 쓰므로 사람이 적는다. 절이 없으면
  "없다" 와 "안 적었다" 를 가를 수 없어 체커가 FAIL 한다. 종결 시 그 행을 원장에 올린다.
- 🔴 **수정 시도에도 상한을 둔다. 라운드 상한과 다른 축이다.** 위 3 라운드는 *리뷰↔반영*,
  이것은 **한 지적을 고치려는 재시도**(권장 **3회**). 네 번째 손을 대고 있으면 원인 진단이
  틀린 것이다. 멈추고 지적·시도·관측을 정리해 보고한다.
- **분리된 주체의 산출도 그대로 받지 않는다.** 가드레일·검증 명령·문서 규약에 비춰 검토한 뒤
  반영한다. 분리는 자기 채점을 막는 장치이지 무조건 옳다는 보증이 아니다.
- 리뷰 브랜치는 필요할 때만 만들고 **사용 후 제거**한다.

## 수동 gate 기록 규약

`CHECK` 가 없는 gate 는 박스 + EVIDENCE 에 글자만 있으면 통과한다. **EVIDENCE 의 품질이 곧
그 gate 의 품질**이다. 도구는 원장에 `WEAK` 로 표시한다.

1. **EVIDENCE 는 세 요소를 갖는다.** *누가·언제* · *무엇을 관측했나(관측값)* ·
   *어디서(환경·버전)*. "확인함"·"정상 동작" 은 증거가 아니라 주장이다.
2. **결과는 이분이다 — 충족 / 미충족.** `부분` 은 리뷰 서술에서는 정당하지만 **gate 판정에는
   쓰지 않는다**. 반만 충족한 gate 는 **항목을 쪼갠다**. 회색 표기는 "일단 넘어감" 의 은신처다.
3. **미충족에는 네 요소를 적는다.** 현상·원인·수정·재검증. 한 줄 요약만 남기면 실패가 증발한다.
4. **다음 라운드에는 미충족만 다시 싣는다.** 충족분은 *"N라운드에서 충족"* 한 줄로 갈음한다.
   기계 gate 는 매번 재렌더라 해당 없음.
5. **실시하지 않은 것을 "해당없음" 으로 적지 않는다.** 불가능하면 `ABANDON:` 으로 드러낸다.
6. **수동 gate 가 늘면 관측 가능성부터 의심한다.** 한 Task 에 3개를 넘으면 명세가 기계 판정
   가능한 형태가 아니라는 신호다.

## 순환 방지 규칙 (필수)

수정과 측정의 순서를 정하지 않으면 "코드를 고치면 측정 무효 → 재측정하면 다음 라운드가 또
코드를 고침" 이 무한히 돈다.

1. **지적을 고칠 때는 그 지적을 재현하는 회귀 테스트를 함께 넣는다.** 최소 구성: 결함을
   재현하는 **RED 확인** · **양방향 경계**(미탐지를 막았으면 과탐지도) ·
   **임계값 체커에 mutation 등록** · 판정자가 여러 소비 지점에 걸치면 **모든 지점** 단정.
2. **테스트는 실제 경로를 지나야 한다.** 중간 자료구조를 손으로 만들면 변환 이음새(seam)를
   건너뛴다. 입력은 **호출자가 실제로 주는 형태**로.
3. **비싼 측정은 코드 지적이 마른 뒤 한 번만.** 순서 고정: **지적 소진 → 최종 측정 1회 →
   이후 문서 변경만 허용**. 문서만 바뀌면 측정은 유효하다.
4. **측정 근거에 측정 커밋 sha 를 적는다.** 확인하는 것은 *sha 가 HEAD 와 같은가* 가 아니라
   **그 sha 이후 `docs/` 밖이 바뀌지 않았는가**. 🔴 문서 규약 체커가 **진행 중 Task 에서**
   기계로 본다. **종결한 Task 는 다시 재지 않는다.**
5. **기능을 삭제하면 감사를 다시 돌린다.** 그 계약을 지키던 테스트가 함께 사라졌으면 그린은
   침묵이다. 테스트는 기능 경계가 아니라 **입력 경계**로 나뉘어 있다.
6. **도달 어려운 분기는 임시 주입으로 태우고, 원복을 gate 로 단정한다.** 환경이 그 분기를
   만들어 주지 않는 것은 **미검증의 사유가 아니다**. 🔴 주입 코드가 남으면 **그 자체가
   결함**이므로 원복은 기억이 아니라 **종결 gate** 로 단정한다. **고정 마커 상수**를 쓰고
   gate 는 규약 2 **부정형 단정** 형태로 적는다. 마커 실재를 함께 단정하지 않으면 이름을 바꾼
   순간 영원히 초록이 된다.

## 임계값·경계값 규칙 (필수)

- 임계값을 도입하면 **경계 정확값 · 경계 −1 · 경계 +1** 세 지점을 테스트한다.
- 계약 수치는 **절대값으로도 못박는다.** 상수 참조 단정만 있으면 상수를 바꿔도 테스트가 따라
  움직여 감지되지 않는다.
- 새 임계값은 임계값 체커(`check_thresholds.py` `MUTATIONS`; 비-Python 은 `PROJECT.md` 검증 명령
  표의 대체 수단)에 등록한다. `SURVIVED` 는 **경계 미보호**이며, 도달 불가일 때만 **사유와
  함께** 예외 처리한다.
